## Важно: чему уже научились на hh-jobs (не повторяй эти ошибки)

1. **НЕ хардкодить регионы/ID.** В hh-jobs придумали SEARCH_AREA_ID=110 без
   проверки — оказалось неверно. Здесь ТЗ явно требует: region/professional_role
   ID получать динамически через `GET https://api.hh.ru/areas` и
   `GET https://api.hh.ru/professional_roles`, не хардкодить.
2. **Проверяй реальную структуру API-ответа**, не угадывай поля — сходи
   `curl https://api.hh.ru/vacancies?text=IT+Manager&schedule=remote&per_page=5`
   и посмотри реальный JSON перед тем как писать парсер полей.
3. **CREATE TABLE должен содержать ВСЕ колонки сразу**, включая те что
   понадобятся позже (notified_at, digested_at — по аналогии с hh-jobs, где
   их забыли и пришлось чинить миграцией задним числом). Смотри схему в
   разделе 6 ТЗ и добавь notified_at/digested_at сразу.
4. **Не int-делить skills_score на весь список навыков.** В hh-jobs была
   формула `matched/len(all_skills)` — при большом списке навыков (200+)
   это математически обнуляет все скоры, т.к. ни одна вакансия не упомянет
   весь список. Используй `matched / TARGET_SKILL_MATCHES` (TARGET ~8-10),
   капается в 1.0. Прежде чем считать MVP готовым — прогони на 5-10 реальных
   вакансиях и убедись что скор адекватно калибруется (не все 0%, не все 100%).
5. **Русские слова склоняются по падежам.** "виртуализация" не совпадёт с
   "виртуализации" через точное сравнение строк — матчи по совпадению
   слов должны использовать основу слова (обрезать 2 последних символа для
   русских слов длиннее 6 символов) или word-boundary regex, не голую
   Python-подстроку `in`. Короткие термины (AI, L1, AD, BI — 4 символа и
   короче) матчить ТОЛЬКО по границе слова (`\bAI\b`), иначе "AI" ложно
   сработает внутри "detail"/"training".
6. **Exclude-фильтр проверять по границе слова**, не голой подстрокой —
   иначе короткие термины типа "техник" ложно сработают внутри "техника
   безопасности" (стандартная фраза почти в каждой вакансии).
7. **Валюта.** Зарплата может быть в RUB/KZT/USD — конвертировать в USD
   перед сравнением с MIN_SALARY_USD, не сравнивать сырые числа. Курс —
   любой публичный источник (см. ТЗ раздел 5), задокументировать откуда
   и что не live-курс, если обновляется не чаще раза в сутки.
8. **notify()/notify_digest() должны БИТЬ длинные сообщения на несколько
   Telegram-сообщений** (лимит Telegram ~4096 символов), НЕ обрезать текст
   с "(truncated)" — иначе теряется хвост списка вакансий.
9. **Защита от параллельного запуска.** Используй `fcntl.flock` на
   lock-файл (`logs/.hh-remote-jobs.lock`) в начале main() — если процесс
   уже выполняется, второй запуск должен сразу выйти, не читая/отправляя
   повторно те же вакансии. В hh-jobs без этого реально ушли задвоенные
   сообщения в Telegram при параллельном запуске.
10. **Проверка рабочего окна (START_HOUR/END_HOUR из .env) — в самом коде**
    main.py, а не только понадеяться на планировщик. В hh-jobs launchd
    StartCalendarInterval дважды подряд не сработал в нужный час несмотря
    на то что ноутбук не выключался — используй планировщик просто как
    триггер (интервал, не привязка к конкретным часам), а окно проверяй
    в коде.

## Задача (Фаза 1 — MVP, без блокеров из ТЗ раздела 10)

1. **`src/hh_client.py`** — клиент к hh.ru API (публичный поиск вакансий,
   OAuth не нужен для чтения):
   - `get_areas()` / `get_professional_roles()` — динамические справочники
   - `search(keywords, schedule='remote', period=7)` — поиск по hh.ru,
     пагинация через page/per_page, уважать `X-RateLimit` заголовки ответа
     (пауза между запросами)
   - Проверь на этапе реализации: `api.hh.kz` — отдельный домен с той же
     структурой, или нужно использовать `api.hh.ru` с фильтром по area
     Казахстана? Задокументируй что выяснил в STATUS.md.
2. **`src/matcher.py`** — скоринг по правилам из `profile_1.env` раздел 12
   + общие разделы (skills, exclude, hard_stop, signal/antisignal keywords).
   Читай веса/термины из `.env` этого проекта (`MY_SKILLS`, `EXCLUDE_KEYWORDS`,
   `HARD_STOP`, `SIGNAL_KEYWORDS`, `MIN_SALARY_USD` и т.п.) — не хардкodить
   логику фильтров в коде, .env — источник правды (см. ТЗ раздел 3).
3. **`src/responder.py`** — Telegram-уведомления в тему TELEGRAM_THREAD_ID
   (сообщение: должность, компания, зарплата в USD и исходной валюте, score,
   ссылка). По аналогии с `hh-jobs/src/responder.py` — можешь взять его как
   референс структуры (не копировать вслепую, там были баги, см. пункт 8 выше).
4. **`src/main.py`** — оркестрация: parse (hh.ru + hh.kz) → match → notify +
   digest (порог 0.70 / 0.40-0.70, batch-лимиты из .env). Lock-файл и
   time-window guard — см. пункты 9-10 выше.
5. **SQLite** — схема по ТЗ раздел 6, дополненная notified_at/digested_at
   с самого начала.
6. **requirements.txt** — уже создан, дополни если нужно.
7. Прогони end-to-end реально (не мокать), убедись что хотя бы одно
   Telegram-сообщение реально доходит в тему 52.
8. Обнови `STATUS.md` (создай, если нет) — что сделано, что проверено вживую,
   какие решения принял на месте реализации (hh.kz домен, курс валют,
   TARGET_SKILL_MATCHES калибровка) и почему.

## Критерий готовности MVP

- `python src/main.py` реально парсит hh.ru (и hh.kz, если получилось
  разобраться с доменом) вакансии со `schedule=remote`
- Скоринг даёт осмысленный разброс (не все 0%, не все 100%) на реальных
