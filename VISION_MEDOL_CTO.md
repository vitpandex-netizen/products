## Почему CTO ≠ Senior Developer

Многие ошибочно считают, что CTO — это «самый крутой программист». Это не так. CTO — это:

| Это НЕ | Это |
|--------|-----|
| Писать код 8 часов в день | **Выбирать** ЧТО писать и ЗАЧЕМ |
| Контролировать каждую строчку | Выстраивать **систему контроля качества** |
| Самому фиксить баги | **Предотвращать** баги через процессы и архитектуру |
| Учить джуниоров React | Нанимать сильных инженеров и **не мешать им работать** |

**Мой профиль:** 19 лет в IT — от системного администратора до IT Director крупных предприятий. Я управлял:

- Командами от 5 до 50+ человек
- Бюджетами от $50K до $5M+
- Enterprise-инфраструктурой с zero-downtime
- Проектами полного цикла — от брифа до продакшена

Я не писал код последние 10 лет. И это **моё преимущество**, а не недостаток.

## Как я вижу свою роль как CTO Medol AI Lab

### Три уровня ответственности

### Уровень 1: Стратегия — куда идём

**Что делаю:**
- **Product Discovery:** Каждую неделю провожу анализ рынка — конкуренты, тренды, gaps. Какие продукты актуальны, какие умирают
- **Roadmap:** Определяю, что делаем в этом квартале, а что откладываем. Не «всё сразу», а фокус на 1-2 продуктах
- **Monetization first:** Перед тем как писать код — отвечаем на вопрос «кто за это заплатит и сколько»
- **Tech selection:** Выбираю стек не потому что «это модно», а потому что решает задачу с минимальными cost + time

**Пример для Customs AI:**
```
Текущая ситуация:  Есть платформа, но нет API, нет интеграций, нет enterprise-продаж
Моя стратегия:     Не фигачить новые фичи. API-first → интеграции → pricing → Sales
                   Только после выхода на $10K MRR — новые продукты
```

### Уровень 2: Процессы — как делаем

**Что делаю:**
- **Архитектурные ревью:** Ни один новый модуль не идёт в продакшен без моего approval. Не контролирую код — контролирую архитектуру
- **Sprint-планирование:** 2-недельные спринты. Каждый понедельник — демо. Каждый вторник — планирование
- **Quality gates:** Автоматические тесты, code review, staging перед production. Без этого — ни одна строчка не идёт в прод
- **Technical debt management:** 20% времени команды — на рефакторинг и тесты. Это не «простой», это инвестиция
- **On-call и SLA:** Продукт работает 24/7? У нас чёткий process для инцидентов

**Мой принцип:** Хороший процесс позволяет команде из 3 человек делать работу команды из 10.

### Уровень 3: Люди — кто делает

**Что делаю:**
- **Hiring:** Я не ищу «разработчика». Я ищу инженера, который думает, а не просто пишет. Собеседую на:
  - Архитектурное мышление
  - Product awareness
  - Ownership
  - Техническую глубину
- **Team structure:**
  ```
  Для Customs AI: 2 backend + 1 frontend + 1 ML Engineer + 1 QA
  Для R&D:        2 ML Researcher + 1 Data Engineer
  ```
- **Mentoring:** Еженедельные 1:1 с каждым. Не контроль — а помощь снять блокеры
- **Culture:** Код-ревью без токсичности, ошибки = уроки, blame-free environment

## Как я буду управлять разработкой НЕ будучи разработчиком

### 1. Architecture Review Board

Я не читаю код. Я читаю **архитектурные документы**:

```
Перед началом разработки любого модуля команда готовит:
1. RFC (Request for Comments) — 1 страница описания решения
2. Sequence diagram — как это работает
3. API contract — что приходит и уходит
4. Data model — какие таблицы меняются
5. Cost estimate — сколько это стоит (инфра + время)
```

Я утверждаю архитектуру. Код пусть пишут — я проверю результат через тесты и демо.

### 2. Quality metrics (вместо чтения кода)

| Метрика | Как меряю | Цель |
|---------|-----------|------|
| **CI pass rate** | GitHub Actions | >95% |
| **Bug reopening rate** | Пошёл в прод, вернулся | <5% |
| **Deployment frequency** | Сколько релизов в неделю | >3 |
| **MTTR** | Среднее время фикса | <4ч для P0 |
| **Code coverage** | Автоматически | >70% |
| **API response time** | p95 | <500ms |

Если метрики зелёные — я не лезу в код. Если красные — разбираемся вместе.

### 3. Decision framework

Когда команда не может решить между двумя техническими подходами:

```
1. Какой подход быстрее доставит ценность пользователю?
2. Какой проще поддерживать через 6 месяцев?
3. Какой дешевле в эксплуатации?
4. Какой масштабируется без переписывания?
```

Если ответы совпадают — решение очевидно. Если нет — решаю я, на основе бизнес-приоритетов.

**Я — CTO, который понимает бизнес.** Разработчики-CTO заканчивают лабораториями. Enterprise-CTO строят продукты, которые продаются.
